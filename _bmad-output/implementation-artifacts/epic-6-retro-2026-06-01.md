## 잘 됐던 것들

### 아키텍처 패턴 일관성
`services/` 레이어 분리, `queryKeys.ts` 중앙 집중 관리, optimistic update 패턴이 Epic 1에서 확립된 후 Epic 6까지 단 한 번도 무너지지 않았다. 신규 서비스(calendar.py, stats.py) 추가 시 "어디에 뭘 넣어야 하는지" 고민이 없었다.

### feat → fix → done 사이클
모든 스토리에서 구현 → 코드 리뷰 수정 → 완료 처리 사이클이 일관되게 유지됐다. 특히 Story 6.1은 코드 리뷰 수정 커밋이 없었는데, 이전 스토리들을 통해 패턴이 충분히 익숙해진 결과로 판단된다.

### 끊김 없는 개발 흐름
전체 스프린트 동안 blocker가 없었고 흐름이 한 번도 끊기지 않았다. (Catty 확인)

### 꾸준한 테스트 커버리지 성장
회귀 없이 테스트가 지속적으로 늘었다. 스토리마다 신규 테스트를 추가하는 습관이 자연스럽게 자리 잡혔다.

## 개선할 것들

### 코드 리뷰에서 반복된 패턴
스토리마다 코드 리뷰에서 비슷한 유형의 문제가 발견됐다:

- **입력값 유효성 검사 누락** (Story 6.1: `count` 파라미터 `ge=1, le=52` 미설정)
- **엣지케이스 미처리** (Story 6.1: `completion_rate > 100%` 방지 로직 누락, `_parse_dt` N×P 중복 호출)
- **Story 6.2 수정 6건**: 누락된 null 처리, 캐시 무효화, 테스트 mock 정확도 등

→ 구현 직후, 제출 전 셀프 체크로 예방 가능한 수준의 문제들이다.

### 라우터 등록 순서 의존성
Story 5.1에서 `/todos/calendar` vs `/todos/{todo_id}` 경로 충돌 문제가 발견됐다. main.py 등록 순서로 해결했지만, 아키텍처 문서에 명시되지 않은 암묵적 제약이었다.

### DB 마이그레이션 수동 실행
Story 6.1의 `completed_at` 컬럼 추가처럼 DB 변경이 필요한 경우, SQL 파일 생성과 실제 실행이 분리되어 있어 자동화가 안 된다. 현재 규모에서는 문제없지만, 팀이 커지면 자동화를 고려해야 한다.
